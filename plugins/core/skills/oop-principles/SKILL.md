# 객체지향 설계 원칙

이 스킬은 언어와 상관없는 원칙만 적는다. 언어별로 지키는 방법은 함께 불러온 언어 스킬을 따른다.

| 언어 | 지키는 법 |
|---|---|
| Java/Kotlin | `java:java-style`의 "객체지향 — Java에서 지키는 법" |
| Python | `python:agent-architecture`의 "객체지향 — Python에서 지키는 법" |

## SOLID

### SRP (Single Responsibility Principle)
- 클래스는 변경의 이유가 하나만 있어야 한다.
- "이 클래스는 무엇을 하는가?"에 한 문장으로 답할 수 없으면 분리.
- 서비스가 비즈니스 로직 + 이메일 발송을 함께 하면 위반.

### OCP (Open/Closed Principle)
- 확장에는 열려 있고, 수정에는 닫혀 있어야 한다.
- 새로운 동작 추가 시 기존 코드를 수정하지 않고 인터페이스 구현체를 추가.
- `if/else` 또는 `switch`로 타입 분기하는 코드는 다형성으로 대체 검토.

### LSP (Liskov Substitution Principle)
- 하위 타입은 상위 타입을 대체할 수 있어야 한다.
- 하위 클래스가 상위 클래스의 계약(사전조건, 사후조건)을 위반하면 안 된다.
- "지원하지 않는 기능"이라는 예외를 던지는 메서드가 있으면 LSP 위반 의심.

### ISP (Interface Segregation Principle)
- 클라이언트가 사용하지 않는 메서드에 의존하면 안 된다.
- 인터페이스가 5개 이상의 메서드를 가지면 분리 검토.
- 역할별로 인터페이스를 나누고, 필요한 것만 구현.

### DIP (Dependency Inversion Principle)
- 상위 모듈이 하위 모듈에 직접 의존하지 않는다. 둘 다 추상화에 의존.
- 의존 객체를 안에서 직접 만들지 않고 바깥에서 넣어 받는다 (의존성 주입).
- 서비스·에이전트는 구체적인 어댑터 구현체가 아닌 포트(인터페이스)에 의존.

## 캡슐화

- 내부 상태는 바깥에 숨긴다. 바깥에 꼭 필요한 것만 노출.
- 불변 객체 선호: 만들 때 값을 정하고 이후 바꾸지 않는다.
- 컬렉션은 내부 원본 대신 읽기 전용이나 복사본을 돌려준다.
- 내부 상태 변경은 의미 있는 메서드명으로 (예: `activate()` not `setActive(true)`).

## 다형성

- 인터페이스 추출 기준: 구현체가 2개 이상이거나, 테스트에서 가짜로 바꿔 끼워야 할 때.
- 추상 클래스 vs 인터페이스: 공통 상태/로직이 있으면 추상 클래스, 순수 계약이면 인터페이스.
- 타입 검사(`instanceof`, `isinstance`) 분기가 반복되면 다형성으로 대체.

## 객체 생성

- 객체는 자기 자신을 생성할 책임을 가진다. 생성 방법과 검증을 그 클래스 안에 둔다.
- 객체가 존재하는 순간 유효해야 한다. 잘못된 값으로는 만들어지지 않게 생성 시점에 검증한다.
- 생성 의도가 여러 가지면 **이름으로 표현**한다 (예: 새로 만들기 `create`, 저장소에서 되살리기 `restore`, 다른 것으로부터 만들기 `from`).

## 디자인 패턴

- 패턴은 문제가 있을 때 적용. 미리 적용하지 않는다.
- 적용 시 패턴명을 클래스명에 반영 (예: `OrderFactory`, `PaymentStrategy`).
- 자주 쓰이는 패턴: Strategy(정책 분기), Factory(생성 캡슐화), Template Method(알고리즘 골격).
- 패턴 남용 금지. 단순한 `if/else`로 충분하면 패턴 불필요.

## 조합(Composition) > 상속

- 상속은 "is-a" 관계가 명확할 때만.
- 코드 재사용 목적의 상속은 조합으로 대체.
- 상속 깊이 2단계 이내 권장.
