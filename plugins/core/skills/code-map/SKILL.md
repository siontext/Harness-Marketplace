# 코드 지도

폴더 하나를 읽고, 파일마다 무슨 일을 하는지와 서로 부르는 순서를 한 화면에 정리한다.
읽기 전용이다. 코드를 고치지 않는다.

메서드가 어떤 순서로 도는지까지 보려면 `code-flow`를 쓴다.

## 절차

1. **대상을 정한다.** 인자로 받은 경로를 쓴다. 없으면 지금 대화에서 다루는 폴더를 쓴다. 그것도 없으면 경로를 묻는다.
2. **파일을 모두 읽는다.** 파일 이름이나 폴더 이름으로 역할을 추측하지 않는다. `import`와 실제 호출을 보고 정한다.
3. **파일마다 역할을 한 문장으로 쓴다.** (아래 "역할 쓰는 법")
4. **계층을 정한다.** (아래 "계층 정하는 기준")
5. **부르는 순서를 그린다.** 바깥에서 들어오는 입구부터 외부 시스템까지.
6. **정해진 형식으로 낸다.** (아래 "출력 형식")

파일이 20개를 넘으면 하위 폴더별로 표를 나누고, 맨 위에 폴더별 한 줄 요약을 둔다.
테스트·캐시·생성된 파일은 뺀다. 요청하면 넣는다.

## 출력 형식

순서와 모양을 바꾸지 않는다.

````markdown
`<폴더>` = <이 폴더가 하는 일 한 문장>

| 계층 | 파일 | 역할 |
|---|---|---|
| 입구 | `__init__.py` | ... |
| 오케스트레이션 | `service.py` | ... |

부르는 순서:

```text
호출하는 쪽 → 입구 → 오케스트레이션 ─┬→ 단계 → 외부 연결 → 외부 시스템
                                     └→ 규칙
```

어긋난 점: (있을 때만)
- `파일`: 하는 일은 <계층>인데 <폴더>에 있다.
````

- 표의 행은 부르는 순서대로 둔다 (입구 → 오케스트레이션 → 단계 → 규칙 → 외부 연결 → 자료).
- 파일 하나만 물으면 그 파일의 행 하나와, 그 파일을 부르는 쪽·그 파일이 부르는 쪽만 보여준다.
- 표와 트리 밖의 설명은 3줄 이내로 쓴다.

## 역할 쓰는 법

"파일 = 하는 일" 한 문장으로 쓴다. 읽는 사람이 다시 묻지 않아도 되게 쓴다.

| 규칙 | 나쁜 예 | 좋은 예 |
|---|---|---|
| 무엇을 받아 무엇을 내는지 적는다 | 주문 처리를 담당한다 | 주문 요청을 받아 재고 확인 → 결제 → 저장 순서로 부른다 |
| 파일 이름을 되풀이하지 않는다 | 결제 클라이언트 | 결제사에 HTTP 요청을 보내고 승인 결과를 받는다 |
| 규칙은 내용을 적는다 | 재시도 정책 | 최대 2번, 4xx면 다시 요청하지 않는다 |
| 추상어만 쓰지 않는다 | 흐름을 관리한다 | 답을 확인하고, 틀리면 한 번 더 요청한다 |
| 평가하지 않는다 | 잘 분리된 도메인 객체 | 주문 금액과 할인 규칙을 가진다 |

## 계층 정하는 기준

폴더 이름이 아니라 **그 파일이 실제로 하는 일**로 정한다.

| 계층 | 이런 일을 하면 |
|---|---|
| 입구 | 바깥에서 부르는 함수·엔드포인트를 내보낸다. 실제 부품을 만들어 끼운다(조립) |
| 오케스트레이션 | 유스케이스 하나의 전체 순서를 잡는다. 다른 파일을 순서대로 부르고 결과를 이어 준다 |
| 단계 | 오케스트레이션의 한 단계를 떼어 낸 것. 그 안에 작은 순서가 있다 (예: 호출 → 확인 → 다시 호출) |
| 규칙 | 업무 규칙과 값. 외부를 부르지 않는다 |
| 외부 연결 | HTTP·DB·파일·SDK를 직접 부른다 |
| 자료 | 코드가 읽는 파일 (프롬프트, 설정, 견본) |

프로젝트가 계층 이름을 따로 쓰면(예: domain / application / infrastructure) 그 이름을 쓴다.

### 순서를 잡는 파일이 둘 이상일 때

"오케스트레이션이 두 개"라고 쓰지 않는다. 범위로 나눈다.

- 유스케이스 전체의 순서를 잡는 파일 하나 = **오케스트레이션**
- 그 안의 한 단계를 맡아 작은 순서를 가진 파일 = **단계**

같은 계층의 파일이 서로 부르는 것은 어긋난 점이 아니다. 어긋난 점은 방향이 거꾸로인 의존(규칙이 외부 연결을 부르는 것 등)과, 하는 일과 폴더가 다른 것이다.

## 다른 용어에 빗댈 때

Controller, Service 같은 다른 프레임워크의 용어에 대응시키는 것은 **정의가 정확히 맞을 때만** 한다.

| 용어 | 이 뜻일 때만 쓴다 |
|---|---|
| Controller | HTTP 요청을 받아 응답을 돌려준다 |
| Service | 유스케이스의 순서를 잡는다 |
| Repository | 저장소에 넣고 꺼낸다 |

맞지 않으면 빗대지 않고 하는 일을 그대로 적는다. 프레임워크가 부르는 함수(그래프의 노드, 메시지 핸들러 등)를 Controller라고 부르지 않는다.

## 하지 않는 것

- 코드를 고치지 않는다. 고칠 점을 묻지 않았으면 제안하지 않는다. 어긋난 점은 사실만 적는다.
- 읽지 않은 파일의 역할을 쓰지 않는다. 읽지 못했으면 "읽지 못함"이라고 적는다.
- 같은 내용을 표와 글로 두 번 쓰지 않는다.

## 예

````markdown
`app/order/` = 주문 요청을 받아 결제하고 저장한다

| 계층 | 파일 | 역할 |
|---|---|---|
| 입구 | `router.py` | `POST /orders`를 받아 주문 요청으로 바꾸고 `service.py`를 부른다 |
| 오케스트레이션 | `service.py` | 재고 확인 → 결제 → 저장 순서로 부르고, 결제가 거절되면 예외를 던진다 |
| 단계 | `payment_step.py` | 결제사를 부르고 승인 결과를 확인한다. 실패하면 규칙이 허락하는 만큼 다시 부른다 |
| 규칙 | `order.py` | 주문 금액 계산과 상태 변화 (접수 → 결제됨 → 취소) |
| 규칙 | `retry_policy.py` | 최대 2번, 4xx면 다시 부르지 않는다 |
| 외부 연결 | `payment_client.py` | 결제사에 HTTP 요청을 보내고 승인 결과를 받는다 |
| 외부 연결 | `order_repository.py` | 주문을 PostgreSQL에 넣고 꺼낸다 |

부르는 순서:

```text
앱 → router.py → service.py ─┬→ payment_step.py ─┬→ payment_client.py → 결제사
                             │                   └→ retry_policy.py
                             ├→ order.py
                             └→ order_repository.py → PostgreSQL
```
````
