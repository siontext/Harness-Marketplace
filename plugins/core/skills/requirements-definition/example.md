# 예시

숫자와 결정은 보여 주기 위한 것이다. 실제 프로젝트에서는 사용자와 정한다.

## 예시 1. 은행 CS 상담 에이전트

상담원이 하던 일을 에이전트가 대신하는 경우다. 1단계부터 3단계까지 이어지는 모양을 보여 준다.

### 1.1 업무 흐름

| 순서 | 상담원이 하던 일 | 시스템에서 맡는 곳 (LangGraph 노드) |
|---|---|---|
| 1 | 문의 사항을 파악한다 | 질의 전달 노드 |
| 2 | 답에 필요한 정보를 찾는다 | Retrieving 노드 |
| 3 | 이 고객에게 답해도 되는 문의인지 본다 | 권한 확인 노드 |
| 4 | 찾은 정보로 답하고 참고 링크를 준다 | Answer Generation 노드 |
| 5 | 답할 수 없으면 상담원에게 넘긴다 | 상담원 연결 노드 |

```text
문의 파악 → 정보 조회 ─┬→ (정보 있음) 권한 확인 ─┬→ (답해도 됨) 답변 + 참고 링크
                      │                         └→ (안 됨) 상담원 연결
                      └→ (정보 없음) 상담원 연결
```

갈림길(정보 있음/없음, 답해도 됨/안 됨)은 엣지가 된다.

### 1.2 요구사항

| 번호 | 요구사항 | 나온 곳 |
|---|---|---|
| 1 | 문의 사항을 기반으로 답변에 필요한 관련 정보를 조회할 수 있어야 한다 (Retriever) | 흐름 2 |
| 1-1 | 조회된 데이터가 있으면 그 데이터를 기반으로 문의에 답변해야 한다 (Augmented Generation) | 흐름 4 |
| 2 | 조회된 정보가 없으면 상담원을 연결해야 한다 | 흐름 5 |
| 3 | 조회한 뒤에도 답변할 수 없는 질문이면 상담원을 연결해야 한다 | 흐름 5 |
| 4 | 답변할 때는 참고 링크를 전달해야 한다 (knowledge grounding) | 흐름 4 |
| 5 | 고객 본인의 정보만 조회해야 한다 | 되묻기 |
| 6 | 같은 세션에서 앞의 대화를 이어 답해야 한다 | 구현 방법 |

### 1.3 빠진 것 되묻기

| 경우 | 예 | 정한 것 | 요구사항 |
|---|---|---|---|
| 남의 정보를 요청할 때 | A 고객이 "B 고객 계좌도 조회해 줘" | 답하지 않는다. 권한 확인이 빠지면 에이전트가 답해 버린다 | 5 |

### 1.4 유스케이스

| ID | 유스케이스 | 액터 | 트리거 | 입력 → 출력 | 필요 도구·데이터 | 자율성 | 근거 |
|---|---|---|---|---|---|---|---|
| UC-01 | 문의에 답을 받는다 | 고객 | 문의 입력 | 문의 → 근거 문서와 참고 링크가 있는 답 | 문서 검색, LLM | 자동 | 요구사항 1, 1-1, 4, 6 |
| UC-02 | 답할 수 없는 문의를 상담원에게 넘겨받는다 | 고객 | 정보가 없거나 답할 수 없는 문의 | 문의 → 상담원 연결 | 상담원 연결 시스템 | 자동 | 요구사항 2, 3 |
| UC-03 | 남의 정보를 요청하면 거절받는다 | 고객 | 다른 고객 정보 요청 | 문의 → 거절 안내 | 권한 확인 | 자동 | 요구사항 5 |

시퀀스 다이어그램은 이 세 줄이 구간 세 개가 된다.

### 2. 구현 방법

#### 요구사항 1. 정보 조회

| 필요한 요소 | 무엇 | 왜 필요한가 |
|---|---|---|
| 검색 엔진 | Elasticsearch, PostgreSQL 중 하나 | 문의와 관련된 문서를 찾아야 함 (1) |
| 검색 알고리즘 | BM25, 시맨틱 검색(코사인 유사도, HNSW) | 같은 뜻의 다른 말("사과", "애플")까지 찾을지에 따라 다름 |
| 벡터 DB | 문서를 벡터로 담아 두는 곳 | 시맨틱 검색을 쓰면 필요 |

여기서 3단계(NFR)로 넘길 질문이 생긴다.

- 검색 레이턴시는 얼마여야 하나
- 어떤 검색 알고리즘을 쓸까 (검색 품질)
- Elasticsearch에 벡터 인덱스가 있는데 벡터 DB를 따로 둬야 하나

#### 요구사항 1-1. 답변 생성

| 필요한 요소 | 무엇 | 왜 필요한가 |
|---|---|---|
| LLM | 답을 만드는 모델 | 찾은 정보로 문장을 만들어야 함 (1-1) |
| 대화 저장 | 세션과 메시지를 저장하는 곳 | 앞의 대화를 이어 답해야 함. 이 요소를 뽑다가 요구사항 6을 찾음 |

여기서 3단계(NFR)로 넘길 질문이 생긴다.

- 고객 개인정보가 외부 LLM으로 그대로 나가도 되나
- 세션 저장소와 메시지 저장소를 따로 둬야 하나

### 3. 문제와 NFR

#### NFR-1. 검색 품질과 속도

기능 요구 "검색할 수 있어야 한다"는 두 방식 모두 충족한다. 어느 쪽을 고를지가 NFR이다.

| 비교 | BM25 | 시맨틱 검색 |
|---|---|---|
| "사과"로 검색 | 애플 데이터는 못 찾음 | 사과와 애플 데이터를 모두 찾음 |
| 전처리 | 필요 없음 | 필요함 (문서를 벡터로 바꿈) |
| 검색 레이턴시 | 상대적으로 짧음 | 늘어나서 답이 느려짐 |

"같은 뜻의 다른 말을 찾는 것"과 "빠른 답" 중 무엇이 중요한지는 기획자와 협의해 정한다.

#### NFR-2. 개인정보

> 고객 개인정보는 외부 LLM API로 바로 보내지 않는다. LLM 게이트웨이를 거쳐, 개인정보 처리 기준을 만족하는 LLM(클라우드 관리형 LLM 등)으로 보낸다.

| 안 | 어떻게 | 대신 | 결정 |
|---|---|---|---|
| A | 외부 LLM API를 바로 부름 | 만들기는 쉽지만 개인정보가 그대로 밖으로 나감 | |
| B | LLM 게이트웨이를 거쳐 클라우드 관리형 LLM을 부름 | 게이트웨이를 하나 더 만들어 운영해야 함 | **고름** |

#### 저장소 선택: 세션 저장소와 메시지 저장소

| Claude가 주는 표준 답 | 이 시스템에 맞춘 판단 |
|---|---|
| 세션은 요청이 잦으니 Redis에 캐싱하고, 메시지는 영속화해야 하니 RDB에 둔다 | 세션 요청이 많지 않고 주고받는 횟수가 많은 형태도 아니다. 저장소를 나누면 따로 부르는 횟수가 는다. RDB 하나에 세션·메시지 테이블을 두고 조인한다 |

## 예시 2. 입력 가드레일 노드

"답하면 안 되는 질문"을 LLM이 판정해 막는 공통 노드다. 되묻기와 NFR 정하는 모양을 보여 준다.

### 1.3 빠진 것 되묻기

| 경우 | 예 | 정한 것 | 요구사항 |
|---|---|---|---|
| 판정을 못 할 때 | LLM 시간 초과, 게이트웨이 오류, 코드가 아닌 답 | 막는다 (Fail-closed). 다음 단계로 넘기면 위반인지 모르는 질문이 확인 없이 넘어간다 | 4 |
| 범위 경계에 걸칠 때 | 서비스 분야 질문이지만 이 에이전트가 맡지 않는 것 | 가드레일은 통과시키고, 에이전트가 맡는 곳을 안내한다 | 1-2 |
| 위반 유형 여러 개에 걸칠 때 | 개인정보와 투자 권유가 한 질문에 | 가장 위험한 유형 하나로 거절한다 | 2-2 |

### 2. 구현 방법 — 요구사항 4. 판정 실패

| 필요한 요소 | 무엇 | 왜 필요한가 |
|---|---|---|
| 시간 제한 | LLM 호출에 기다리는 시간 한도를 둠 | 한도가 없으면 응답이 안 올 때 끝없이 기다림 |
| 다시 시도 | 실패하면 한 번 더 부름 | 잠깐의 장애 때문에 바로 고객을 막지 않기 위해 |
| 실패 이유 기록 | 이유는 로그에만 남기고 고객에게는 안내 문구만 보냄 | 운영하는 쪽은 원인을 알아야 하고, 고객에게는 내부 사정을 보여 주지 않음 |

여기서 3단계(NFR)로 넘길 질문이 생긴다.

- 시간 제한을 몇 초로 할까
- 몇 번까지 다시 시도할까
- 가드레일과 에이전트 답변을 합쳐 전체 시간 제한 안에 끝나는가

### 3. NFR-1. 속도

> 가드레일은 어떤 경우에도 3초 안에 끝난다. 전체 3초 예산(Time Budget) 안에서 남은 시간이 있을 때만 한 번 더 부른다.

| 구분 | 숫자 | 출처 |
|---|---|---|
| 정해진 것 | 전체 응답 15초 (API Gateway 시간 제한) | 구성도 |
| 잰 것 | 판정 1번에 평균 1.4초, 가장 오래 걸린 경우 2.7초 | 정확도 테스트 |

| 안 | 어떻게 | 가드레일 최대 | 대신 | 결정 |
|---|---|---|---|---|
| A | 호출 1번 3초, 한 번 더 시도 (기존 코드) | 6초 | 잠깐 장애가 나도 한 번 더 기회가 있음 | |
| B | 호출 1번 3초, 다시 시도 없음 | 3초 | 잠깐 장애에도 바로 오류 문구가 나감 | |
| C | 전체 3초 예산 안에서 남은 시간이 있을 때만 다시 시도 | 3초 | 시간 초과는 다시 시도 못 함. 금방 돌아온 실패만 한 번 더 부름 | **고름** |

- 기존 코드는 A안이다. 4단계에서 고친다.

### 3. NFR-2. 정확도

> 놓침 0건(Recall 100%), 과잉 차단 5% 이하. 놓침을 더 엄하게 본다.

| 틀리는 방식 | 예 | 결과 |
|---|---|---|
| 놓침 (False Negative) | 투자 권유 질문을 통과시킴 | 에이전트가 종목을 추천해 버림. 규제 문제 |
| 과잉 차단 (False Positive) | "보이스피싱 구별법 알려줘"를 막음 | 고객이 답을 못 받음. 불편 |

과잉 차단 5% 이하를 보려면 정상 질문이 100개쯤 있어야 "5개 이하"가 된다. 그래서 테스트셋 크기도 이 자리에서 정한다.
