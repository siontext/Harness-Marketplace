# 요구사항 정의

기능 하나를 맡았을 때 무엇을 만들지부터 숫자 기준까지 사용자와 함께 정한다.
기획자가 정리해 주지 않으면 개발자가 직접 한다(FDE, Forward Deployed Engineer). 이 스킬은 그때 쓰는 순서다.

## 생각하는 법

단계의 순서는 아래 생각에서 나왔다. 어느 단계에서든 막히면 여기로 돌아온다.

1. **에이전트는 사람이 하던 일을 대신한다.** 그래서 그 사람의 업무 흐름이 곧 요구사항이다. 흐름의 단계는 LangGraph의 노드가 되고, 갈림길은 엣지가 된다. "에이전트는 추론 영역이라 명세를 못 쓴다"는 말은 틀렸다. 에이전트의 답도 결국 API 응답(코드, 메시지, 데이터)으로 나간다.
2. **NFR부터 조사하지 않는다.** 기능을 정하고(무엇), 구현 방법을 그리고(어떻게), "이렇게만 구현하면 되나?"를 묻다 보면 NFR이 나온다. NFR 목록부터 늘어놓고 조사하면 과해지고 느려진다. 어차피 설계하는 동안 계속 나온다.
3. **NFR은 고객도 기획자도 말해 주지 않는다.** "답변에 10분 걸려도 되나?", "개인정보가 외부 LLM으로 그대로 나가도 되나?"는 개발자가 먼저 묻는다.
4. **NFR은 숫자만이 아니다.** 그 숫자를 지키려고 무엇을 쓸지(검색 알고리즘, 저장소, 모델) 고르는 것까지 NFR이다. NFR이 정해지면 저장소·모델 선택으로 자연스럽게 넘어간다.
5. **트레이드오프는 안으로 놓고, 결정은 사람이 한다.** 예: A는 답까지 10분 걸리지만 정확하고, B는 5초면 되지만 덜 정확하다. 기획자(사용자)와 협의할 수 있게 표로 보여 준다.
6. **개발자는 현장 지식(암묵지)이 없다. 그래서 되묻는다.** 흐름에 없는 경우를 찾아 "이거 에이전트가 다 답해도 돼요?"라고 묻는다. 예: 권한 확인이 빠지면 A 고객이 "B 고객 계좌도 조회해 줘"라고 할 때 에이전트가 답해 버린다. 꼭 있어야 할 것과 위험한 것(거버넌스)을 이 단계에서 찾는다.
7. **순서는 유기적이다.** 구현 방법을 뽑다가 빠진 요구사항이 나오면 1단계로 돌아가 추가한다. 시퀀스를 그리다 요구사항이 나와도 된다. 단계 표는 지도일 뿐이다.
8. **리서치는 질문이 생겼을 때만 한다.** "메시지를 캐싱해야 하나?" 같은 구체적인 질문이 생기면 "다른 곳은 어떻게 하지?"를 찾는다. 질문 없이 미리 조사하지 않는다.
9. **표준 답은 이 시스템에 맞는지 따진다.** Claude가 내놓는 답은 널리 알려진 표준이다. 이 시스템의 요청량, 주고받는 횟수, 제약에 맞는지 따지고 왜 맞는지 말할 수 있어야 한다. "Claude가 그러던데요"는 근거가 아니다.
10. **시퀀스만 보고 부하를 가늠한다.** 구현하기 전에 연산별로 걸리는 시간(아래 표)을 보고 어디가 느릴지 먼저 따진다. 예: 다른 서버로 보내는 HTTP 요청은 TCP 연결(HTTPS면 인증서 교환까지)을 새로 맺어서, 커넥션을 재사용하는 DB 조회보다 오래 걸린다. 그래서 저장소를 둘로 나눠 따로 부르기보다 DB 하나에서 조인하는 편이 빠를 수 있다. 설계 문서의 시퀀스는 유스케이스마다 구간을 나누고, 바깥으로 나가는 화살표마다 걸리는 시간, 꼭 필요한가, 어느 요구사항·NFR인지를 적어 따진다 (`agent-design-doc` 3절).

| 연산 | 걸리는 시간 |
|---|---|
| L1 캐시 참조 | 1ns |
| 메모리 참조 | 100ns |
| 같은 데이터센터 왕복 | 0.5ms |
| 디스크 탐색 | 10ms |
| 대륙 간 TCP 왕복 | 150ms |

출처: Latency Numbers Every Programmer Should Know. 개발자 머릿속에 들어 있어야 하는 수치다.

정답이 없는 문제라 오래 고민해도 된다. 다만 결정은 한 주제씩 내리고 넘어간다.

## 진행 순서

| 단계 | 하는 일 | 나오는 것 |
|---|---|---|
| 1. 요구사항 정의 | ① 업무 흐름 → ② 요구사항 쓰기 → ③ 빠진 것 되묻기 → ④ 확인 사항 정리 | 흐름 표, 요구사항 표, 되묻기 표, 확인 사항 표 |
| 2. 구현 방법 | 요구사항마다 필요한 요소를 "무엇, 왜 필요한가"로 뽑는다 | 요구사항별 요소 표, 3단계로 넘길 질문 |
| 3. 문제와 NFR | 2단계에서 넘어온 질문을 숫자로 정하고, 그 숫자로 저장소·모델을 고른다 | NFR별 결정 문장, 근거 숫자 표, 안 비교 표 |
| 4. 기존 설계·코드와 맞춰 보기 | 이미 있는 설계 문서·코드를 1~3과 비교해 다른 것만 고친다 | 차이 표 |
| 5. 검증 | 3단계에서 정한 숫자를 실제 환경에서 잰다 | 잰 결과 |

- 단계마다 앞 단계 결과가 다음 단계의 재료가 된다. 2단계 요소에서 3단계 질문이 나오고, 3단계 숫자로 5단계에서 잰다.
- 4단계는 기존 설계·코드가 없으면 건너뛴다.

## 진행 규칙

- **한 번에 한 주제만 다룬다.** 요구사항 하나, NFR 하나씩 다룬다. 메시지마다 결론을 먼저 쓰고 표는 하나만 둔다. 여러 주제를 한 메시지에 묶지 않는다.
- **결정은 사용자가 한다.** 제안은 "이렇게 넣을까요?"로 끝낸다. 사용자가 동의하면(예: "넣어", "ㅇㅇ") 그때 문서에 쓴다.
- **근거를 붙인다.** 요구사항마다 어느 문서의 어디(파일, 시트·셀, 절, 행)에서 나왔는지 적는다. 문서에 없으면 "문서에 없음"이라고 쓰고 누가 언제 정했는지 적는다. 근거를 지어내지 않는다.
- **문서끼리 다르면 하나를 고르지 않는다.** 둘 다 적어 확인 사항(1단계 ④)으로 보낸다. 그동안은 임시로 하나를 따르고 확인 중이라고 적는다.
- **질문은 글로 한다.** 선택지 창(AskUserQuestion)을 쓰지 않는다. 무엇을 보고 묻는지(문서와 위치)를 함께 쓴다.
- **문서는 대화에서 보여 준 그대로 쓴다.** 확인받은 표와 목록을 압축하거나 다시 쓰지 않는다. 말투만 문서체(~다)로 바꾼다. 문서 목차는 진행한 단계 순서를 따른다.
- **NFR 질문은 2단계에서만 나온다.** 3단계에서 새 NFR이 필요해 보이면, 그 질문이 나오는 구현 요소를 2단계 표에 먼저 넣는다.
- **진행 상황 표를 고친다.** 단계가 끝나거나 막히면 문서 맨 위 표의 상태를 바꾼다.
- **다음 단계는 사용자가 시작한다.** 단계가 끝나면 한 일을 짧게 말하고, 다음 단계를 시작할지 묻는다.

## 단계별 하는 법

### 1. 요구사항 정의

**① 업무 흐름**

- 이 기능이 대신하는 사람(상담원, 심사자 등)이 하던 일을 순서대로 적는다.
- 단계마다 시스템에서 어디가 맡는지 옆에 적는다. 이 기능이 맡는 단계는 굵게 표시한다. 다른 곳이 맡는 단계도 지우지 않는다. 경계가 보여야 한다.
- 갈림길이 있으면 표 아래에 `text` 블록으로 흐름을 그린다. 단계는 노드, 갈림길은 엣지다.
- "흐름이 이게 맞나요? 빠진 단계가 있나요?"로 확인받는다.

**② 요구사항 쓰기**

- 이 기능이 맡는 단계를 "~해야 한다" 문장으로 바꾼다. 문장 하나에 요구사항 하나만 쓴다.
- 세부 조건은 1-1, 1-2처럼 붙인다.
- 하지 않는 일도 요구사항이다 (예: "입력만 판정한다. 출력 검사는 다른 곳이 맡는다").
- 이 문서에서 다루지 않는 것(다른 요구사항에서 정할 것)은 표 아래에 따로 적는다.
- "나온 곳" 열에는 흐름 N, 되묻기, 구현 방법 중 하나를 쓴다. 요구사항이 어느 과정에서 나왔는지 보이게 한다.

**③ 빠진 것 되묻기**

흐름에 없는 경우를 아래 질문으로 찾는다. 해당하는 것만 쓴다.

| 질문 | 예 |
|---|---|
| 실패하면? | 외부 시스템 고장, 시간 초과, 형식이 틀린 답. 막을지(Fail-closed) 통과시킬지(Fail-open)를 정한다 |
| 경계에 걸치면? | 범위 안 같기도 하고 밖 같기도 한 입력 |
| 여러 개에 걸치면? | 규칙 두 개에 동시에 걸리는 입력 |
| 이 사람이 요청해도 되나? | 권한. 남의 정보 조회 |
| 앞뒤 단계는 누가 맡나? | 내가 하는 줄 알았는데 남이 하는 것, 그 반대 |
| 여러 곳에서 같이 쓰나? | 공통 모듈, 여러 에이전트 |
| 개인정보는 어디로 나가나? | 외부 LLM, 로그 |

정한 것이 요구사항이면 ②의 표에 "나온 곳 = 되묻기"로 넣는다.

**④ 확인 사항**

- 문서끼리 다르거나 문서에 없어서 임시로 정한 것을, 확인해 줄 사람(기획자, PL)에게 물을 목록으로 만든다.
- 사용자가 원하면 보낼 글로 다듬는다. 보내는 것은 사용자가 한다.

### 2. 구현 방법

- 요구사항마다 표를 하나씩 만든다.
- "왜 필요한가"는 요구사항 번호나 사실(문서, 테스트 결과, 기존 코드)로 쓴다. "좋아서", "일반적으로"는 이유가 아니다.
- 기법에 공식 이름이 있으면 그 이름을 쓴다 (예: LLM-as-a-Judge, Fail-closed, Time Budget).
- 이미 정해진 기술·모델은 누가 언제 정했는지 적는다.
- 하지 않는 일을 정한 요구사항은 요소가 적다. 억지로 채우지 않는다.
- 요소를 뽑다가 빠진 요구사항이 보이면 1단계 ② 표에 추가하고 "나온 곳"을 구현 방법으로 적는다.
- 숫자가 필요한 요소(몇 초, 몇 번, 얼마나 정확하게, 몇 명)가 생기면 그 표 바로 아래에 적는다. 질문이 없는 요구사항에는 쓰지 않는다.

  ```markdown
  여기서 3단계(NFR)로 넘길 질문이 생긴다.

  - 판정에 몇 초까지 써도 되나
  - 얼마나 정확하게 맞혀야 하나
  ```

- 표준 답(Claude가 먼저 떠올리는 답)을 낼 때는 표준 답과 이 시스템에 맞는 이유를 나눠 말한다.

### 3. 문제와 NFR

2단계에서 넘어온 질문을 NFR-1, NFR-2처럼 묶는다. 묶는 이름은 질문에 나온 것만 쓴다 (속도, 정확도, 붐빌 때, 비용, 개인정보, 가용성 등).

NFR 하나는 이 순서로 정한다.

1. **숫자 근거를 모은다.** 정해진 것(문서에 적힌 제한)과 잰 것(테스트 결과)을 출처와 함께 표로 만든다.
2. **안을 만든다.** A, B, C마다 어떻게 하는지, 그 숫자가 어떻게 되는지, 대신 무엇을 잃는지를 쓴다. 기존 코드가 쓰는 방식이 있으면 그것도 안 하나로 넣는다.
3. **사용자가 고르면 결정 문장을 맨 위에 인용(`>`)으로 쓴다.** 표의 결정 열에 "고름"을 표시한다.
4. **남은 것과 주의할 것을 아래에 목록으로 쓴다.** 기존 코드가 다른 안이면 "4단계에서 고친다"고 적는다.

- 정확도는 틀리는 방식을 나눈다. 놓침(False Negative)과 과잉 차단(False Positive)의 결과를 각각 쓰고, 어느 쪽을 더 엄하게 볼지 정한다.
- 비율을 정하면 그 비율이 의미 있으려면 테스트셋이 몇 개 있어야 하는지도 정한다. 예: 과잉 차단 5% 이하를 보려면 정상 질문이 100개쯤 있어야 "5개 이하"가 된다. 21개뿐이면 하나만 막혀도 4.8%다.
- 숫자를 아직 정할 수 없으면(합의 전) 숫자를 지어내지 않는다. 무엇을 따를지와 언제 잴지만 정한다.
- 저장소·모델은 NFR이 정해진 뒤에 고른다. 이미 정해져 있으면 NFR에 맞는지 다시 본다. 저장소를 나눌지는 시퀀스에서 부르는 횟수와 연산별로 걸리는 시간으로 따진다.

### 4. 기존 설계·코드와 맞춰 보기

- 기존 설계 문서와 코드를 읽고 1~3단계에서 정한 것과 비교한다.
- 다른 것만 표로 모은다. 같은 것은 쓰지 않는다.
- 차이를 하나씩 보여 주고, 고칠지 사용자에게 묻는다.

### 5. 검증

- 3단계에서 정한 숫자(시간, 정확도, 부하)를 실제 환경에서 잰다. 테스트셋은 3단계에서 정한 크기로 만든다.
- 기준에 못 미치면 2·3단계로 돌아가 안을 다시 고른다.

## 문서

- 위치: 프로젝트의 `docs/design/`. 없으면 사용자에게 묻는다.
- 이름: `YYYY-MM-DD_<기능>_요구사항.md`
- 처음 확인을 받으면 [template.md](template.md)로 문서를 만들고, 확인받을 때마다 채운다.
- 예시: [example.md](example.md)
- 요구사항이 정해지면 설계 문서로 넘어간다. AI 에이전트는 `agent-design-doc`, 웹 백엔드는 `design-doc`을 쓴다.
