# Implementation Checkpoint

## 목적

페이즈를 시작할 때 무엇을 만들지 먼저 보여주고, 끝낼 때 빌드와 테스트가 진짜 확인하는지를 보고 진행 여부를 묻는다.
한 번에 사람이 검토할 수 있는 양(클래스 1~2개)만 나오게 하고, 다음 페이즈로 넘어가기 전에 빌드를 보장한다.

---

## 체크포인트 절차

구현 단위는 설계 문서의 **구현 페이즈(구현 단계)** 표의 한 행에 대응한다 (예: JPA 엔티티, 도메인 클래스, 서비스, 컨트롤러 / 연결 창구, 도구, 에이전트 흐름, API).  
페이즈마다 "페이즈 시작" → 1 → 5 순서를 따른다.

### 페이즈 시작 — 대상 제시

설계 문서에는 클래스별 상세 명세가 없다. 코드를 쓰기 전에 이 페이즈에서 만들 것을 먼저 제시하고 승인받는다.

- 만들 클래스 목록과 각 클래스의 주요 메서드 시그니처를 제시한다. 구현 본문은 쓰지 않는다.
- 설계 문서의 어느 부분(ER·시퀀스·API 계약·비즈니스 규칙·도구 표 등)에서 나온 것인지 한 줄로 밝힌다.
- 메인 브리지 형식으로 승인을 요청한다 (형식은 4단계 참고).
  - prompt: `"[페이즈명]에서 다음을 만들려 합니다: <클래스 목록>. 이대로 작성할까요?"`
  - header: `"페이즈 시작"`
  - options:
    1. `"작성 (Recommended)"` — 제시한 구성으로 코드 작성
    2. `"구성 변경"` — 클래스 구성·시그니처 조정 필요
- 승인 후 코드를 작성하고 1단계로 넘어간다.
- "구성 변경" 회신 시 자유 입력으로 조정 내용을 받아 다시 제시한다.

### 1. 빌드 확인 실행

프로젝트 언어에 맞는 확인 명령을 실행한다. 나열한 명령이 모두 통과해야 성공이다.

| 언어 | 확인 명령 |
|---|---|
| Kotlin | `./gradlew compileKotlin` |
| Java | `./gradlew compileJava` |
| Python | `.venv/bin/ruff check .` → `.venv/bin/ruff format --check .` → `.venv/bin/pyrefly check` → `.venv/bin/pytest -q` (테스트 파일이 아직 없으면 pytest는 건너뛴다) |

이하 "컴파일"은 이 표의 확인 명령 전체를 뜻한다.

### 2. 컴파일 실패 처리

- 실패 시 오류 메시지를 분석하고 수정한다.
- 3회 연속 실패하면 현재 상태를 사용자에게 보고하고 중단한다.

### 3. 변이 테스트 — 테스트가 진짜 확인하는지

컴파일이 통과하면, 이번 페이즈의 테스트가 코드가 하려는 일을 진짜 확인하는지 본다. 커버리지는 테스트가 그 줄을 지나갔다는 뜻일 뿐, 그 줄이 맞는지 확인했다는 뜻이 아니다.

- 원본은 그대로 두고, 복사본에서 이번 페이즈 코드를 한 곳씩 일부러 틀리게 바꾼 뒤 테스트를 돌린다 (Mutation Testing). 테스트가 실패하면 잡힌 것이고, 그래도 통과하면 놓친 것이다.
- 바꿔 볼 곳: 이번 페이즈에서 새로 쓰거나 바꾼 검사(`if … throw/raise`), 분기 조건, 경계값, 상수, 꼭 불러야 하는 호출(저장·닫기 등).
- 변이마다 바꾼 코드와 관련된 테스트만 먼저 돌린다. 거기서 안 잡힌 변이만 전체 테스트로 다시 돌린다. 관련 테스트에서 잡힌 변이는 전체로 돌려도 잡히므로, 결과는 처음부터 전체로 돌린 것과 같고 시간만 줄어든다.
- 놓친 것은 테스트를 보강하고 1단계부터 다시 한다. 테스트로 드러나지 않는 코드면 그 코드가 필요한지부터 본다.
- 작은 수정(`team-workflow`의 "단계마다 품질 확인" 기준)은 이 단계를 건너뛰고, 4단계 보고에 "안 함 (작은 수정)"으로 적는다.
- 언어별 방법은 그 언어의 테스트 스킬에 있다 (Python: `python:python-testing`의 "변이 테스트"). 방법이 적혀 있지 않은 언어는 이 단계를 건너뛰고, 4단계 보고에 "안 함"으로 적는다.

### 4. 사용자 승인 요청

컴파일과 변이 테스트가 끝나면 확인한 것을 보고하고 사용자에게 진행 여부를 묻는다.

보고는 확인마다 결과를 표로 적는다. 하지 않은 확인은 "안 함"과 이유를 적는다. 하지 않은 것을 했다고 쓰지 않는다.

| 확인 | 결과 |
|---|---|
| 컴파일 (1단계 명령 전체) | 통과 |
| 변이 테스트 | 바꾼 N곳 중 N곳 잡힘 (놓친 곳과 보강한 테스트) / 안 함 (이유) |

- 설계 원칙·읽기 쉬움·코드 냄새 같은 품질 기준은 구현 에이전트가 자기 코드를 스스로 판정하지 않는다. 메인이 독립 검토로 확인한다 (`team-workflow`의 "단계마다 품질 확인"). 보고에 "검토했다"고 쓰지 않는다.

> **메모:** subagent는 `AskUserQuestion`을 직접 호출할 수 없다 (anthropics/claude-code#34592). 아래 형식의 **옵션 명세**를 부모(메인) Claude에 텍스트로 반환하면, 메인이 사용자에게 클릭 UI로 띄우고 답변을 다시 전달한다.

- prompt: `"[단위명] 구현 완료. 계속 진행할까요?"` (예: `"Entity 구현 완료. 계속 진행할까요?"`)
- header: `"체크포인트"`
- options:
  1. `"계속 (Recommended)"` — 다음 구현 단위로 진행
  2. `"수정 요청"` — 현재 단위 보완 후 컴파일 재실행
  3. `"설계 변경 필요"` — 설계 문서 자체를 갱신해야 함

"계속" 회신 시 → 5단계(승인 후 처리)로 이동한다.  
"수정 요청" 회신 시 → 사용자의 수정 내용을 파악하고 반영한 뒤 1단계(컴파일 실행)부터 재시작한다.  
"설계 변경 필요" 회신 시 → 6단계(설계 변경 처리)로 이동한다.

### 5. 승인 후 처리

- 사용자가 승인하면 다음 구현 단위로 넘어간다.
- 사용자가 수정을 요청하면 해당 사항을 반영하고 1(컴파일 실행)부터 다시 시작한다.

### 6. 설계 변경 처리

사용자가 "설계 변경 필요"를 선택한 경우:

1. 메인에 자유 입력 요청을 보내 변경 내용을 받는다 (`options` 없이 `prompt`만 반환).  
   예시 prompt: `"어떤 부분의 설계를 변경해야 하나요?"`
2. 작업을 중단하고, 사용자에게 다음을 안내한다:
   - 설계 변경 사유와 현재 구현 상태를 요약해 전달한다.
   - designer 에이전트를 호출하여 설계 문서를 업데이트하도록 안내한다.
   - 설계 문서가 업데이트되면 구현 에이전트를 다시 호출하여 변경된 설계 기준으로 해당 단위부터 재구현한다.
3. `<promise>IMPL_BLOCKED_DESIGN_CHANGE</promise>`를 출력하고 종료한다.

---

## 규칙

- 커밋은 이 스킬에서 수행하지 않는다. 커밋은 리뷰 에이전트가 검증 통과 후 담당한다.
- 단위 완료 조건: 해당 단위의 모든 파일이 작성되고 컴파일이 통과되고, 변이 테스트에서 놓친 곳이 없는 상태 (방법이 없는 언어와 작은 수정은 컴파일 통과까지).
