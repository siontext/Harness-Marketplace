# 하네스 작업 흐름

## 맡기는 순서

| 단계 | 에이전트 | 플러그인 |
|---|---|---|
| 설계 | `designer` | core |
| 구현 | `backend-dev` (Java/Kotlin) / `python-dev` (Python) | java / python |
| 리뷰·커밋 | `java-reviewer` (Java/Kotlin) / `python-reviewer` (Python) | java / python |
| PR·문서 | `pr-docs` | core |

- 무엇을 만들지(요구사항)가 아직 정리되지 않았으면 설계 전에 `requirements-definition`으로 사용자와 먼저 정한다. 한 주제씩 사용자 확인을 받아야 해서 서브에이전트에게 맡기지 않고 메인이 직접 진행한다.
- 브레인스토밍·설계 단계에서는 `oop-principles`와 프로젝트 언어의 아키텍처 스킬(Java: `java:layered-architecture`, Python 에이전트: `python:agent-architecture`)을 참조한다.
- 설계 문서 양식: 웹 백엔드 기능은 `design-doc`, AI 에이전트는 `agent-design-doc`.
- 설계 방향이 정해지면 문서 작성은 `designer`에게 맡긴다.
- 코드 검증·리뷰는 프로젝트 언어의 리뷰 에이전트에게 맡긴다.

## 단계마다 품질 확인 (메인)

구현 에이전트가 체크포인트(`implementation-checkpoint`)를 보내면, 사용자에게 전하기 전에 메인이 아래를 한다. 구현 에이전트의 보고만 보고 "확인했다"고 하지 않는다. 리뷰 에이전트(`java-reviewer` / `python-reviewer`)의 설계 정합성 검증과는 별개다.

수정이 크든 작든 아래를 모두 한다. 대신 검토는 **바뀐 곳과 영향 범위**만 읽힌다. 범위가 좁으면 검토도 금방 끝나므로, 작은 수정이라고 건너뛰지 않는다.

- 영향 범위: 바뀐 줄이 든 함수·메서드 전체, 그것을 부르는 곳, 그것을 확인하는 테스트.
- 바뀌지 않았고 영향 범위에도 없는 코드는 다시 읽히지 않는다. 그 대신 테스트는 늘 전체를 돌리고(1번), 마지막 전체 검토(5번)는 빼지 않는다.

1. **검사 다시 돌리기** — 체크포인트의 컴파일·테스트 명령을 메인이 직접 다시 실행한다. 테스트는 바뀐 곳과 상관없이 전체를 돌린다.
2. **독립 검토** — 결론을 모르는 읽기 전용 검토자(`general-purpose` 서브에이전트)에게 이번 단계에서 바뀐 곳과 영향 범위를 읽힌다.
   - 기준: 객체지향·SOLID, 읽기 쉬운 코드, 코드 냄새, KISS·DRY·YAGNI, 테스트가 함수가 하려는 일을 확인하는지(커버리지를 채우려는 테스트가 아닌지), 버그.
   - 검토자에게는 코드 위치, 기준, 프로젝트가 정한 규칙(문제로 보지 말 것)만 준다. 메인의 판단이나 "문제없다"는 결론은 주지 않는다. 결론을 주면 검토자가 그 결론을 확인해 주는 쪽으로 기운다.
   - 검토자는 파일을 고치지 않는다. 변이 테스트를 할 때는 복사본에서만 한다.
3. **지적 재현** — 지적마다 메인이 코드 줄을 직접 확인하거나 재현해 본 뒤 사용자에게 전한다. 재현되지 않은 지적은 "재현 못 함"으로 나눠 적는다.
4. **고친 코드도 다시** — 지적을 고친 코드도 같은 기준으로 다시 읽힌다. 고치다 생긴 문제는 고친 코드에만 있다. 검토자에게는 고친 줄(diff)과 그 영향 범위만 준다. 파일 전체를 다시 읽히지 않는다. 영향 범위까지 주는 것은 고친 줄이 주변 코드와 어긋나는지도 보이게 하려는 것이다.
5. **마지막에 전체 한 번 더** — 모든 단계가 끝나면 전체 코드를 한 번 더 독립 검토한다. 단계 사이에 걸친 중복이나, 처음부터 끝까지 따라가야 보이는 문제는 그때만 보인다.

사용자에게는 기준마다 누가 확인했고 결과가 어땠는지 표로 보고한다. 확인하지 않은 기준은 "안 함"으로 적는다. 확인하지 않은 기준을 "확인했다"고 말하지 않는다.

| 기준 | 누가 | 결과 |
|---|---|---|
| 컴파일·테스트 | 메인 (다시 실행) | 통과 |
| 변이 테스트 | 구현 에이전트 | 바꾼 N곳 중 N곳 잡힘 |
| 객체지향·SOLID, 읽기 쉬움, 냄새, KISS·DRY·YAGNI | 독립 검토자 → 메인 재현 | 지적 N개, 고침 N개 |
| 고친 코드 다시 읽기 | 독립 검토자 | 안 함 (이유) |

## 요구사항 추적표

요구사항마다 어떤 코드가 맡고, 어떤 테스트가 확인하고, 끝났는지를 한 표로 둔다. 날짜별 기록이나 설계 문서만으로는 "어느 요구사항이 아직 안 끝났는지"가 한눈에 안 보이기 때문이다. 프로젝트 현황을 정리할 때 이 표의 상태 칸을 읽는다.

- **위치**: 설계 문서 옆 `docs/specs/<기능>/요구사항-추적표.md`
- **만들 때**: 첫 구현 단계를 시작할 때 메인이 요구사항 문서의 번호와 문장으로 줄을 만들고, 구현 코드·테스트 칸은 비워 둔다.
- **고칠 때**: 단계마다 품질 확인이 끝나면 메인이 그 단계에서 생긴 구현 코드·테스트와 상태를 채운다. 설계 문서의 미정 번호에 걸려 끝나지 않은 줄은 상태에 그 번호를 적는다.
- **형식**:

| # | 요구사항 | 구현 코드 | 테스트 | 상태 |
|---|---|---|---|---|
| 1 | 주문 번호로 주문 상태 조회 | `service.py` `OrderService` | `test_order_service.py` | 확인 끝 |
| 2 | 배송 전 주문만 취소 | `order.py` `Order.cancel` | `test_order.py` | 환불 정책 답 남음 (Q-1) |

- 상태는 "확인 끝" 또는 "<무엇> 남음"으로 쓴다. "진행 중"처럼 무엇이 남았는지 안 보이는 말은 쓰지 않는다.

## 리뷰가 불통과(FAIL)일 때

1. 리뷰 문서의 "미해결 이슈"를 구현 에이전트(`backend-dev` / `python-dev`)에게 넘겨 고치게 한다. 설계 문서를 바꿔야 하는 문제면 `designer`에게 먼저 넘긴다.
2. 고친 뒤 리뷰 에이전트를 다시 실행한다.
3. 이 반복이 3번 넘게 불통과면 멈추고 사용자에게 상황을 알린다.
- 에이전트 정의 파일(`plugins/<플러그인>/agents/<이름>.md`)에 적힌 사용자 질의 브리지 형식을 따른다. 서브에이전트는 `AskUserQuestion`을 직접 띄울 수 없어서 메인이 중계한다.

## 서브에이전트 실행·정리

- 서브에이전트는 background(`run_in_background`)로 띄우지 않고 **`name`을 붙여 포그라운드 teammate로** 띄운다. tmux pane에 진행 상황이 보여야 한다.
- 서브에이전트가 작업을 마치고 idle 알림을 보내면 결과를 회수한 뒤 바로 정리한다. idle 상태로 두지 않는다.
- 이유: "완료 시 자동 정리" 설정이 없다. background는 pane이 안 떠서 진행이 안 보이고, 포그라운드는 끝나도 idle로 대기한다.

## 금지 명령

`core` 플러그인의 PreToolUse 훅(`hooks/deny-guard.py`)이 `hooks/deny-rules.json`에 적힌 명령을 실행 전에 차단한다. 차단되면 메시지에 나온 대체 방법을 쓰거나 사용자에게 직접 실행을 요청한다.

## Python 프로젝트 명령

`python` 플러그인의 명령은 사용자가 직접 부를 때만 실행한다. Claude가 알아서 실행하지 않는다.

| 명령 | 하는 일 |
|---|---|
| `/python:new` | 정해진 뼈대로 새 프로젝트 만들기 |
| `/python:export` | 검사 통과 후 반출용 압축 파일 만들기 |
| `/python:eval` | 실제 LLM으로 평가 질문 실행 (비용 발생) |
